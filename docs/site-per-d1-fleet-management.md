# 多请求分组清单与发布协调

`operations/fleet/p1.json` 明确列出 P1 分组、A/B 原始 schema 所有权凭证，以及 C、D 两份不可变建站请求。维护端按顺序读取中央日志，将每一步的已建库 UUID 合入下一份清单；历史请求只作为来源证据，不能把 C 的三站清单重新上传覆盖当前四站。

`resolveProvisionFleet` 支持一次明确选择至多 20 组、每组至多 50 站的清单解析；这些是输入上限，不是已验证的生产容量。每个组必须有完整的已完成建站历史。除原始 P1 A/B 外，所有成员均来自所列的建站操作，不能把来源不明的数据库作为“历史基线”导入。新分组可从空基线及其首个已完成操作开始，Worker/D1 等资源仍须由原受限建站流程准备，本模块不会创建它们。

## 证据与隔离

解析器核对存储计划与输入完全一致、checkpoint 6、没有未完成步骤、六步回执齐全；数据库、schema、资料归属、原部署清单摘要、核验部署与激活站点相互对应。它再用中央登记逐项核对当前 D1/binding、站内 ID、schema、分组和可信后台域名。登记版本不能早于激活回执。暂停站可保留，迁移中或已退役成员阻止普通发布。

历史顺序不可跳过或重排，下一操作的基线必须与前一操作的结果完全相同。跨组重复站点、数据库、站内 ID、Worker 或 Worker tag 一律拒绝；公开/私有桶可按全局稳定 siteId 前缀跨组共享，但不能交叉充当另一种角色，也不能指向中央存储。混合 schema 版本及来源迁移需另接渐进迁移流程，不能放宽这些核对。

解析仅使用中央只读查询，不对历史请求、回执、路由、权限或数据库内容做修改。每组输出当前清单、摘要、各站核验凭证以及各原始操作的计划/回执摘要。部署控制器在上传前重读并核对同一结果，实际 API 资源和 runtime binding 校验继续由既有控制器执行。

## 逐组发布和恢复

`releaseProvisionFleet` 按明确顺序调用原有持久化组发布器。每组独立保存上传结果并验收，成功结果立即交给报告回调；中间组失败即停止后续组，不假设多 Worker 存在原子事务。重入复用之前已完成组的回执，恢复失败组的同一次上传，不重复上传已知结果。建站预约、发布互斥、180 秒租约/30 秒续期和四个运维租约总上限继续由中央日志执行。

P1 控制器已改用此解析器和发布协调器，仍明确只选它现有的一个四站远程分组。它同时核对最后的 D 请求与现有部署入口一致，四站核验目标改由历史清单生成，并与显式目标文件比较。新路径必须通过真实四站回归、逐表只读核验及最终生产版本检查。
