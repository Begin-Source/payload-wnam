## 执行器

[seed.ts](../scripts/site-operations/seed.ts) 接受中央/站点独立 Payload 实例、明确 D1 和原操作计划。它验证中央 schema 回执、站点 schema 所有权、账号与租户仍存在，并核对已有记录的稳定 ID、租户、负责人及注册信息。无原种入意图的已有记录拒绝接管，已完成回执但记录缺失或权限改变时拒绝自动恢复。

只读模式不领取租约、不登记路由、不写资料或回执。apply 使用既有 180 秒租约/30 秒心跳，在效果发生前持久记录 seed 意图。中央 journal 操作始终留在中央上下文；每次本地 Payload 写入使用独立的站点上下文和 D1 绑定。

执行顺序为：登记 `provisioning` 路由 → 复制租户显示资料 → 建立负责人身份投影 → 创建本地站点 → 创建中央站点元数据 → 登记站长权限 → 核验后提交 seed 回执。中央站点由真实负责人作为创建主体，保留 Payload 的默认值和业务 hooks。站点库没有中央密码、密码哈希、会话或组织角色副本；显示身份不自行授予运行时权限。

两个 D1 之间没有跨库事务。故障发生后根据原意图、schema 所有权和已写入的稳定身份逐项恢复，已存在且一致的资料记录只读，不重新种入，也不重置名称等可编辑资料。apply 返回的 `mutations` 表示是否执行种入写入；即使该值为 false，执行租约的领取、心跳和释放仍会写中央操作日志，不能将它解读为整个调用没有数据库写入。只有 dry-run 不写日志。回执的 `contentDigest` 明确只摘要 `{databaseId,siteId,localSiteId,tenantId,ownerUserId}`，不能用来证明未来文章内容或全部配置的哈希一致性。

首次种入演练在实际站点 D1 已有租户、身份和站点记录，而中央站点元数据尚未创建时主动抛出异常。随后另一执行器调用恢复并再次重复检查。该演练是明确代码边界上的异常注入，不声称模拟真实断网或杀死进程。
