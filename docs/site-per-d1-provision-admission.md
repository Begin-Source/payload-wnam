# 中央建站申请与执行交接

中央建站界面需要把人员输入交给受限云端建站流程。`src/site-control/provisionAdmission.ts` 实现持久申请、按租户读取和取消；`scripts/site-operations/admission.ts` 保存经过云端规划器核对的完整请求；新增 D1 触发器把申请与现有 `ProvisionJournal.reserve` 原子连接。当前代码位于 `feat/site-provision-admission`。申请 HTTP 与后台表单已接线并通过云端验证；尚未部署到远程中央服务，也未启用自动云端建站，不能当作已完成的建站入口。

## 输入与权限

人员输入严格限定为 requestId、永久 siteId、名称、租户、负责人和 IANA 时区。请求 ID 也是后续建站操作 ID；重试不能改变申请内容或提交人。浏览器不能提交账号凭据、数据库 UUID、本地数字 ID、binding、Worker、代码路径或生产开关。

提交、读取和取消均要求原始中央会话仍有效。建站权限来自中央数据库中明确保存的 `super-admin` / `system-admin` 角色，或属于目标租户的 `general-manager`；不能把现有单站 manager 权限扩展成租户建站权限。环境邮件超管快捷配置本身不授予这个资源创建能力。负责人必须属于目标租户或具有明确的跨租户管理员角色，账户不能锁定。写语句再次核对权限与会话，不能只依赖先前异步读取。

同一 siteId 最多存在一个未取消申请，已登记或已有建站操作的网站拒绝新申请。读取摘要不返回准备的基础设施清单、租约或密钥。取消保留原申请；取消完成后可用新请求 ID 重新申请同一尚未建站的 siteId。

提交语句同时分配站内数字 ID，取中央站点记录、登记、建站日志和历史申请所占编号的最大值加一。分配与申请 INSERT 同属一条原子语句；重试保留原编号，取消也不释放编号。准备计划必须匹配该编号，预约触发器阻止另一个维护操作抢占它。没有向浏览器开放基础设施编号选择或历史申请删除入口。

## 交接与恢复

云端规划器须先核对当前完整分组、实际 deployment、绑定、容量及 schema，再调用 `prepareProvisionAdmission`。该函数严格解析完整请求，逐项匹配人员输入，把完整请求 JSON、规范计划和摘要持久保存；此时仍未创建资源。保存后只能重用完全相同的计划，不能在重试时悄悄更换基础设施选择。

预约建站的同一条 D1 INSERT 触发核对：申请未取消、已经准备、计划及摘要相同、提交人和负责人当前权限有效。通过后申请原子变为 provisioning；任何失败使预约回滚。另一操作 ID 也不能抢占已有申请的 siteId。取消只能发生在预约前，因此取消和预约的竞争有确定结果。已预约操作继续使用原六步日志及恢复机制，不再允许用取消申请来冒充外部资源回滚。

原有无申请来源的审定维护操作仍使用原日志。HTTP/MCP 不直接获得 `ProvisionJournal` 或 Cloudflare 账号 Token；前端也不会调用准备函数。已完成状态由原操作的完成回执派生，不另造独立的成功标记。

## 动态规划与完整分组历史

`scripts/site-operations/admission-plan.ts` 从明确选择的已审定分组规划资源：读取完整历史及当前登记，要求检查适配器返回经过实际资源核对的 deployment/清单，使用申请已分配的数字 ID 和由请求 UUID 派生的 binding，匹配调用方提供的构建 schema，再保存完整计划。同组最多保留一份尚未预约的准备计划；其他组可以独立准备。已准备或已预约的申请重用原计划，不因为重试而换库、换组或换 schema。真实 Cloudflare 检查适配器和构建产物读取已在验证分支接线；建库和上传继续使用受限六步执行器。

`scripts/site-operations/admission-fleet.ts` 从中央持久申请中接回已完成的新站。它按完整基线清单连接后续操作，不依赖请求文件中的“最后一个站”或时间戳顺序。重复列出的操作必须完全相同，断链或分叉拒绝合并；最终仍经过既有完整历史解析器的计划、六步回执、schema、当前登记和跨组冲突核对。因此后续发布可获得新增站点的完整清单及独立核验凭证。未完成的新站不伪装成已完成成员，规划器也不会隐式创建未审定的新 Worker 分组。

这些模块当前属于验证分支的维护逻辑。普通发布控制器已在分支内改为读取动态历史，尚未替换远程部署版本。规划测试使用原生中央 D1；资源检查器测试通过实际 API 客户端处理受控 HTTP 响应，不作为真实 Cloudflare 资源执行证据。

### 云端规划命令

`site:plan` 在 Cloudflare Builds 的审定部署分支中运行，要求本次提交匹配 release marker、已检查的站点角色产物与 schema、明确账号以及仓库中审定的 fleet 路径。不得在本地执行或为执行而伪造 CI 环境。

```sh
pnpm run site:plan --request-id <申请UUID> --group p1-group-1 --fleet operations/fleet/p1.json --dry-run
pnpm run site:plan --request-id <申请UUID> --group p1-group-1 --fleet operations/fleet/p1.json --prepare
```

`--dry-run` 只读取中央 D1 和 Cloudflare API，不保存准备计划、不预约操作。新计划预览仍核对当前提交人/负责人权限和分组冲突，但不锁定资源；稍后准备可能因状态变化拒绝或产生不同部署基线。`--prepare` 保存不可变完整申请，属于中央 D1 写入，仍不创建数据库、不上传 Worker。输出位于本次云端工作目录 `.cloudflare-ci/admission/<申请UUID>/`：预览为 `preview-request.json`，持久准备为 `request.json`，另有模式对应报告。日志只输出选择、摘要、路径和执行范围，不输出完整人员申请或凭据。

首次规划的真实 API 适配器在资源检查前后核对同一部署、版本与 release 标记，要求完整绑定和 provision 来源一致，核对账号/zone、中央和站点 Worker tag、中央/全部站点 D1 名称与关闭读副本、R2 区域及禁止直接公开访问、各后台域名归属和关闭 workers.dev/预览。它特别核对最近完成站点的 D1，不能只查上一份请求的历史基线。完整目标清单必须由最近一次不可变请求推导，不能通过自写 JSON 或重算摘要删掉旧站点。

已准备或已预约请求返回原样保存的计划，不重新选择基线；报告中的 expectedDeploymentId 是原计划约束，不宣称重入时的实时部署版本。后续六步执行器仍须执行自己的实际资源检查、预约及恢复。此云端命令尚未在远程中央 v5 上执行，尚未挂接自动触发；不得把命令代码存在当作真实新站创建通过。动态清单已在分支的普通发布控制器内接线并通过云端验证，仍须完成远程发布后才执行新增申请。

### 后续构建触发方式

2026-09-18 核实：Workers Builds 的 Deploy Hook 可绑定指定分支，由服务端 POST 启动构建；Hook URL 本身是凭据。平台只在构建 queued/initializing 时合并重复触发，运行后的再次 POST 可产生新构建。[Cloudflare 官方说明](https://developers.cloudflare.com/workers/ci-cd/builds/deploy-hooks/)

据此选择后续由中央服务端保存固定分支的 Hook secret，人员申请先持久化，再由有状态的投递记录触发；Hook URL 不进入浏览器、申请 JSON、源码或日志。需要保存 build UUID、核对构建终态并处理触发结果不明，不能把一次 POST 成功当作建站成功，也不能依赖 Hook 的短暂去重替代原子预约和恢复。此触发适配器尚未实现或创建 Hook；本轮只完成文档与接口核实，没有改动远程构建配置。

## 中央表单与 HTTP 接口

`CentralProvisionRequests` 扩展现有中央“我的网站”后台，沿用 Payload 主题和按钮。人员显式选择所属租户、负责人，填写站点 ID、名称和时区；候选项仅来自其建站权限范围。普通站点经理没有授权租户时不显示申请区。提交返回的是持久申请，页面明确说明自动执行尚未启用，不能把等待状态当作建站完成。

所有接口只挂在中央角色，要求真实 Payload JWT 原会话；读取结果为 `private, no-store`，写入要求严格同源 Origin、2 KiB 内 JSON，拒绝额外字段、重复或未知查询参数。没有 Cloudflare Token、Worker 或 D1 ID 的浏览器字段，也没有在请求路径调用资源创建器。

- `GET /auth/site-provision-options?kind=tenants[&after=<id>]`：按权限分页返回租户名称；`kind=owners&tenantId=<id>` 返回该租户可选负责人邮箱。每页最多 50 条。
- `GET /auth/site-requests?tenantId=<id>[&after=<requestId>]`：按创建时间和请求 ID 倒序分页，保留取消记录；每页最多 50 条，不读取站点 D1。
- `GET /auth/site-request?requestId=<uuid>`：读取当前申请摘要；完成状态来自原建站日志。
- `POST /auth/site-request`：严格六项人员输入，复用原申请编号及原子分配的站内数字 ID。
- `POST /auth/site-request-cancel`：仅接受 requestId；预约开始后取消返回冲突，不伪装外部资源回滚。

表单提交结果不明时锁定原输入并重试同一请求 ID，避免重复创建。输入错误允许修正；取消采用行内确认，取消响应丢失后仍可重试同一申请。切换租户清理负责人选择和列表分页；撤权后的读取拒绝并清空列表。自动执行、派发及状态对账仍待下一步接通。
