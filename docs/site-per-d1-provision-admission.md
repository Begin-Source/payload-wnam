# 中央建站申请与执行交接

中央建站界面需要把人员输入交给受限云端建站流程。`src/site-control/provisionAdmission.ts` 实现持久申请、按租户读取和取消；`scripts/site-operations/admission.ts` 保存经过云端规划器核对的完整请求；新增 D1 触发器把申请与现有 `ProvisionJournal.reserve` 原子连接。当前代码位于 `feat/site-provision-admission`，尚未挂载 HTTP/界面，也未安装到远程中央数据库，不能当作已可用的建站入口。

## 输入与权限

人员输入严格限定为 requestId、永久 siteId、名称、租户、负责人和 IANA 时区。请求 ID 也是后续建站操作 ID；重试不能改变申请内容或提交人。浏览器不能提交账号凭据、数据库 UUID、本地数字 ID、binding、Worker、代码路径或生产开关。

提交、读取和取消均要求原始中央会话仍有效。建站权限来自中央数据库中明确保存的 `super-admin` / `system-admin` 角色，或属于目标租户的 `general-manager`；不能把现有单站 manager 权限扩展成租户建站权限。环境邮件超管快捷配置本身不授予这个资源创建能力。负责人必须属于目标租户或具有明确的跨租户管理员角色，账户不能锁定。写语句再次核对权限与会话，不能只依赖先前异步读取。

同一 siteId 最多存在一个未取消申请，已登记或已有建站操作的网站拒绝新申请。读取摘要不返回准备的基础设施清单、租约或密钥。取消保留原申请；取消完成后可用新请求 ID 重新申请同一尚未建站的 siteId。

提交语句同时分配站内数字 ID，取中央站点记录、登记、建站日志和历史申请所占编号的最大值加一。分配与申请 INSERT 同属一条原子语句；重试保留原编号，取消也不释放编号。准备计划必须匹配该编号，预约触发器阻止另一个维护操作抢占它。没有向浏览器开放基础设施编号选择或历史申请删除入口。

## 交接与恢复

云端规划器须先核对当前完整分组、实际 deployment、绑定、容量及 schema，再调用 `prepareProvisionAdmission`。该函数严格解析完整请求，逐项匹配人员输入，把完整请求 JSON、规范计划和摘要持久保存；此时仍未创建资源。保存后只能重用完全相同的计划，不能在重试时悄悄更换基础设施选择。

预约建站的同一条 D1 INSERT 触发核对：申请未取消、已经准备、计划及摘要相同、提交人和负责人当前权限有效。通过后申请原子变为 provisioning；任何失败使预约回滚。另一操作 ID 也不能抢占已有申请的 siteId。取消只能发生在预约前，因此取消和预约的竞争有确定结果。已预约操作继续使用原六步日志及恢复机制，不再允许用取消申请来冒充外部资源回滚。

原有无申请来源的审定维护操作仍使用原日志。HTTP/MCP 不直接获得 `ProvisionJournal` 或 Cloudflare 账号 Token；前端也不会调用准备函数。已完成状态由原操作的完成回执派生，不另造独立的成功标记。

## 动态规划与完整分组历史

`scripts/site-operations/admission-plan.ts` 从明确选择的已审定分组规划资源：读取完整历史及当前登记，要求检查适配器返回经过实际资源核对的 deployment/清单，使用申请已分配的数字 ID 和由请求 UUID 派生的 binding，匹配调用方提供的构建 schema，再保存完整计划。同组最多保留一份尚未预约的准备计划；其他组可以独立准备。已准备或已预约的申请重用原计划，不因为重试而换库、换组或换 schema。真实 Cloudflare 检查适配器和构建产物读取尚待接线；建库和上传继续使用受限六步执行器。

`scripts/site-operations/admission-fleet.ts` 从中央持久申请中接回已完成的新站。它按完整基线清单连接后续操作，不依赖请求文件中的“最后一个站”或时间戳顺序。重复列出的操作必须完全相同，断链或分叉拒绝合并；最终仍经过既有完整历史解析器的计划、六步回执、schema、当前登记和跨组冲突核对。因此后续发布可获得新增站点的完整清单及独立核验凭证。未完成的新站不伪装成已完成成员，规划器也不会隐式创建未审定的新 Worker 分组。

这两个模块当前属于验证分支的维护逻辑，尚未替换 P1 固定 D 请求的远程发布入口。新的规划测试使用原生中央 D1 和受控外部检查结果，不作为真实 Cloudflare 资源执行证据。

### 后续构建触发方式

2026-09-18 核实：Workers Builds 的 Deploy Hook 可绑定指定分支，由服务端 POST 启动构建；Hook URL 本身是凭据。平台只在构建 queued/initializing 时合并重复触发，运行后的再次 POST 可产生新构建。[Cloudflare 官方说明](https://developers.cloudflare.com/workers/ci-cd/builds/deploy-hooks/)

据此选择后续由中央服务端保存固定分支的 Hook secret，人员申请先持久化，再由有状态的投递记录触发；Hook URL 不进入浏览器、申请 JSON、源码或日志。需要保存 build UUID、核对构建终态并处理触发结果不明，不能把一次 POST 成功当作建站成功，也不能依赖 Hook 的短暂去重替代原子预约和恢复。此触发适配器尚未实现或创建 Hook；本轮只完成文档与接口核实，没有改动远程构建配置。
